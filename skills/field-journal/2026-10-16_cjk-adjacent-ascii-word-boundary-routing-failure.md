# 中文紧贴 ASCII 关键词导致 \b 词边界失效（路由层静默回退）

**日期**: 2026-10-16
**场景分类**: 其他（工具/路由层缺陷，非目标逆向）
**目标**: 本地逆向技能路由包自身（非外部目标）

## 背景

用真实中文任务描述调用路由器时，明显属于某个具体路由的任务却落到 `fallback`（通用兜底）。
官方回归基准全绿（178/178），说明缺陷不在规则内容，而在**匹配语义**。

## 根因

`.NET`（PowerShell `-match`）与 Python 3 `re` 的 `\w` 在 Unicode 字符串下**都包含 CJK 字符**，
因此 `\b`（词边界）在「汉字紧贴 ASCII 关键词」时**两边都是 word 字符 ⇒ 无边界 ⇒ 断言不成立**：

```
输入「分析这个APK有没有加固」
  "个"(CJK, \w) 与 "a"(ASCII, \w) 相邻 ⇒ 不是词边界
  \bapk\b 不成立 ⇒ 所有提该路由的规则全不命中 ⇒ 落兜底
```

**为什么基准没发现**：既有 103 条中文用例**全部用空格隔开** ASCII 关键词（如「安卓 APK 加固」），
从未覆盖「汉字紧贴」这种真实输入习惯。**基准的覆盖盲区，比缺陷本身更值得记。**

## 量化

| 引擎 | 修复前 | 修复后 |
|------|--------|--------|
| PowerShell（.NET Regex） | 11/20 正确 | 18/20 |
| Python（bash 路由入口用它） | **0/8 正确** | **8/8** |

两个平台读同一份规则文件 ⇒ 一次修复同时覆盖两边。剩余 2 条不匹配是**有意保留**：
裸 `so` / `elf`（不带点号）不匹配 —— 加了会误伤英文常用词。

## 修复

把 `must` / `mustAll` / `exclude` 里的 `\b` 全部换成 **ASCII-only 边界断言**：

```
\bX\b   ->   (?<![A-Za-z0-9_])X(?![A-Za-z0-9_])
```

要点：
- **只动正则字段**，`note`（说明文字）里的 `\b` 保持原样（那是散文，不是正则）。
- 判定某个 `\b` 是前边界还是后边界时，**优先看左邻字符**：左邻是 ASCII word char ⇒ 后边界；
  否则右邻是 word char ⇒ 前边界。实测按「优先看右邻」实现会把 `ad\b.?cs` 这种判错，导致 `.` 匹配不上。
- 改完必须跑回归基准（本次 178 → 197 仍全绿）。

## 踩坑记录

| 问题 | 原因 | 解决方案 | 耗时 |
|------|------|---------|------|
| 替换后 JSON 非法 | 磁盘上正则 `\b` 是**3 个字符**（转义反斜杠 + b），按 2 字符替换会吃掉 `\` | 二进制/精确匹配 3 字符序列 | 20 min |
| 改完文件 diff 巨大 | Python text mode 读写把换行符转换了 | **二进制读写**，不做换行转换 | 15 min |
| 基准全绿但功能坏 | 基准用例与真实输入习惯不一致（带空格 vs 不带） | 补 15 条「无空格」用例锁定回归 | 10 min |

## 可复用的模式

**「基准全绿 ≠ 功能正确」的判据**：用**真实用户措辞**（而非用例措辞）抽样跑一遍。
本例的真实措辞特征就是「中英文之间无空格」。任何做文本匹配的系统都该问一句：
「我的测试输入和用户真实输入，在**分词边界**上一样吗？」

## 对本包的改进建议

- 基准用例应显式包含「同一关键词的两种写法（带空格 / 紧贴）」作为**配对用例**，避免单侧覆盖造成的假绿。
- 若上游采纳，规则层建议统一用 `(?<![A-Za-z0-9_])` 而非 `\b`，因为本包面向**中英混排**用户。
- `references/` 里可补一页「Unicode 词边界陷阱」（含 JS 侧同样问题：JS 的 `\w` 是 ASCII-only，所以 JS 实现**没有**这个 bug —— 三引擎行为不一致本身是坑）。
