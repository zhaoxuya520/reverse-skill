# 2026-09-26 上传返回成功但业务未入账的权威回读核验

## 场景分类

Web / API 业务数据一致性核验，非漏洞利用。

## 目标概述

客户端上传接口返回成功，但用户在业务账本中看不到记录。通过稳定业务唯一键、权威回读接口和分层状态机，区分“请求已受理”“业务已入账”“业务已入账但不计分”与“确实未入账”。

## 完整执行链路

1. 收集三类证据：客户端上传响应、用户可见业务列表、同源只读查询结果。不要把单一成功提示当成最终结果。
2. 寻找稳定业务唯一键。理想键应同时出现在上传响应和权威业务账本中，并且编码格式、作用和生命周期一致。
3. 排除伪唯一键：HTTP 状态码、请求时间、数据库自增编号、列表位置、客户端本地编号都可能变化或无法跨系统匹配，不能作为最终对账依据。
4. 用少量成功与失败样本建立时间线。重点观察业务键从哪一步开始缺失，以及缺失样本是否集中在某个入口、版本或时间范围。
5. 验证回读接口是否真的适用于当前业务体系。检查鉴权状态、响应内容类型、分页边界、分月条件、数据保留窗口和接口版本；兼容接口返回内容不一定代表主流程仍然有效。
6. 区分“暂时查不到”和“权威否定”。当高质量同源接口明确给出不符合资格、无有效业务对象或计划不可用时，应记录该否定结论，不要继续用旧对象或兼容接口拼出一条看似成功的路径。
7. 建立分层状态机：

| 状态 | 含义 | 典型处理 |
|------|------|----------|
| accepted | 请求已被接收，但业务结果未知 | 等待权威回读，不计入成果 |
| effective | 权威账本命中且满足业务计分条件 | 计入额度、次数和展示指标 |
| ineffective | 权威账本命中但明确不计分 | 保留可见记录，不占用额度，允许按业务规则重试 |
| pending | 暂未命中，但仍处于合理处理窗口 | 延迟重查，不立即判失败 |
| missing | 超过处理窗口且权威回读完整，仍未命中 | 标记失败，进入重试或人工核验 |
| unknown | 回读链路不可用或语义无法确认 | 告警并保留原状态，不做成功推论 |

8. 在写入面增加前置闸门：业务唯一键缺失、资格明确否定或当前对象不可用时，应在产生副作用前中止，并向调用方返回可区分的失败原因。
9. 在读数面拆分指标：只有 effective 计入有效成果；ineffective 单独展示；pending 保留等待态；missing 可重试；unknown 触发告警。成功请求数量不能直接等同于业务有效数量。
10. 先做只读影子核验，对比新旧判定结果，再逐步启用写入闸门。上线后按日回放最终状态，检查是否存在长期 pending、错误 ineffective 或额度重复占用。

## 踩坑记录

| 问题 | 原因 | 解决方案 | 耗时 |
|------|------|----------|------|
| 上传成功但账本无记录 | 成功响应只证明请求被接收，不证明业务关联已建立 | 以上传响应中的稳定业务键回读权威账本 | 主要排查时间 |
| 兼容接口让人误判 | 旧对象仍可被查询，但当前业务对象已明确不可用 | 先记录权威否定，再决定是否允许兼容查询 | 数轮只读探针 |
| 跨月数据查不到 | 账本按业务月份分区并有分页上限 | 按目标月份读取，并翻页到结束条件 | 一轮探针 |
| 旧体系恒返回未找到 | 查询接口只覆盖新体系，旧体系没有对应语义 | 为每个体系分别建立键映射和判定规则 | 数轮探针 |
| 已入账记录被误报失败 | 接口表示“已收录但不计分”，未与“未收录”区分 | 增加 ineffective 状态并单独告警 | 一轮探针 |
| 看板把请求成功当成有效成果 | 指标只统计请求层成功状态 | 按 accepted 与 effective 分层统计 | 一轮端到端验收 |
| 时间窗口边界记录被漏掉 | 查询条件使用滚动时间范围，边界样本滑出 | 对边界记录执行单条回读，并记录查询条件 | 少量补核验 |

## 工具链发现

- 只读探针应先于业务代码修改。先用少量样本确认键关系和状态语义，再把规则固化到状态机。
- 回读接口需要单独记录“版本、覆盖范围、分页/分月规则、响应类型、限流策略”，否则同一接口在不同客户端下可能得到不同结论。
- 变更前做一次全量账号的键来源矩阵，可以同时验证修复覆盖面、兼容分支占比和潜在误伤范围。
- 用匿名样本夹具覆盖 effective、ineffective、pending、missing、unknown 五类状态，比只测成功路径更容易发现指标和重试逻辑缺陷。

## 对本包的改进建议

- 在 API 安全参考中增加“上传后回读对账”检查清单：
  1. 上传响应的业务语义是什么；
  2. 哪个字段是跨系统稳定唯一键；
  3. 哪个接口是权威回读源；
  4. 回读是否分页、分月或有时间窗口；
  5. 是否存在“已入账但不计分”等复合状态；
  6. 权威否定后是否仍错误地使用兼容兜底；
  7. 额度、报表和告警是否只消费有效状态；
  8. 是否有真实样本覆盖所有状态；
  9. 是否执行过只读影子核验和小流量上线。
- 在报告模板中明确区分“接口请求成功”“业务对象创建成功”“业务最终生效”三个层次，避免把 transport 成功写成业务成果。

## 可复用的模式/脚本片段

1. 假成功三问：接口返回什么，权威账本以什么键保存，两者能否精确对应。
2. 稳定键矩阵：按入口、客户端版本、业务体系和日期范围列出业务键来源，找出缺口和交叉关系。
3. 权威否定优先：同源权威结果明确否定时，不再用低置信兼容接口恢复执行。
4. 双轴状态机：请求层使用 accepted 等状态，业务层使用 effective、ineffective、pending、missing、unknown，两层不可混用。
5. 可观测重试：无效记录可见但不占用有效额度；暂时未命中进入延迟重查；未知状态只告警，不猜测成功。
6. 先读后写：先以只读工具确认键和状态语义，再修改写入闸门、指标和重试策略。
